## P0 fixes

### Hash-aware rollback

`_rollback` never blindly restores backups. For each entry:

- current == new hash: Crew wrote it; restore backup if valid;
- current == old hash: untouched/already restored; do not touch;
- current is a third version: preserve it, mark `RECOVERY_REQUIRED`;
- missing/corrupt backup: `RECOVERY_REQUIRED`, no overwrite;
- all restores use temp file + atomic replacement; exceptions are reported,
  never marked as successful rollback.

This makes a pending entry unable to destroy a human edit created after the
backup.

### Recovery cannot silently skip corruption

- Invalid journal JSON → preserve file, write `RECOVERY_REQUIRED` marker and
  block new publishes.
- Journal paths (`rel`, `backup`, `generated`) are validated against their
  roots; malicious/escaping paths block recovery.
- Journals are written before/after each operation; an interruption between
  `os.replace` and journal update is detected by comparing destination hashes.
- Recovery is idempotent and reports failure instead of claiming success.

### Path and symlink safety

- Paths are validated at manifest time, before directory creation, immediately
  before each replacement, and during recovery.
- Symlink components in destination paths are rejected; journal backup and
  generated paths must remain inside the journal directory.
- A per-project publish lock (`publish.lock`) blocks concurrent publishers.

### WorkspaceManifest

`validate_workspace_integrity` compares every prepared original with the
workspace:

- preserved/modified originals pass;
- a missing original fails publication unless an approved `DeletionOperation`
  with the matching expected hash covers it;
- new files pass;
- excluded files are N/A and listed with reason.

## P1 fixes

### Ignore safety

`IgnoreRules` applies, in order:

1. mandatory security exclusions (`.env`, `.env.*` except `.env.example`/
   templates, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`, `.ssh`, `.aws`);
2. explicit includes from `.crewignore`/`.gitignore` (`!pattern`), never
   overriding security;
3. technical exclusions (`.venv`, `.git`, `bin`, `obj`, `.vs`,
   `.vscode`, `node_modules`, `dist`, caches, …);
4. `.crewignore`;
5. `.gitignore` additional patterns.

The preparation report records excluded paths and reasons.

### Approved DeletionOperation

`DeletionOperation(target_file, expected_sha256, requirement_id, reason)` is
part of `ArchitectureContract` and therefore the architecture approval hash.
Deletions require a valid requirement id and expected hash; they are backed up,
journaled, reversible, and rejected if the original changed or is a protected
security file. LLM-inferred deletions are not accepted as a workflow feature.

### Recovery Manager CLI

```bash
crew-tui --resolve-publish-conflict --project DIR
crew-tui --resolve-publish-conflict --project DIR \
  --journal ID --file REL --choice human|original|generated|manual \
  [--manual-file PATH]
```

The journal keeps immutable generated snapshots and originals. A choice other
than the tested generated version sets `REVALIDATION_REQUIRED` and does not
mark `DONE`; generated-only resolution can commit. No JSON editing is needed.

## Journal states

`PREPARED → PUBLISHING → COMMITTED`; on failure
`ROLLING_BACK → ROLLED_BACK` or `RECOVERY_REQUIRED`; conflict resolution may
produce `REVALIDATION_REQUIRED`. Per-file entries carry their own state.

journal**, not a global multi-file atomic transaction. Documentation now says
